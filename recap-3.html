Session 03 · Recap · Sunday, November 22, 2026

Make objects visible

Your traffic lights made the case for objects before we said the word. We talked through why objects help, followed confetti from repeated variables to parallel arrays to a class of its own, and heard from artist Joshua Davis about what happens when you ask for a thousand of something.

Before December 6

Grow the confetti

Open the confetti lesson in Pickcode. It has two files: Sketch.java, a Times Square New Year’s Eve scene, and Confetti.java, the class. In the Processing editor, paste the sketch into a new sketch and the class into a second tab named Confetti. The same steps and the starter code are in the Google Classroom assignment. Try what you have time for, and bring it to the start of Session 4.

  1. Predict. Read both files before running them. What will you see? What happens when you click?
  2. Run. Run it a few times, and click a few times. Were you right?
  3. Investigate. Which constructor does setup() call? What would new Confetti(100) do? Why does drawConfetti call c.getSize() instead of reading the size directly?
  4. Modify. Give each piece its own x and y: private instance variables, set in both constructors, with getters. Use the getters in drawConfetti in place of (400, 80).
  5. Make. Write a fall() method that moves the piece down by its own speed, and call piece.fall() in draw(). When it falls off the bottom, send it back to the top at a random x.
  6. Make more. Put several pieces on the screen. Three variables is fine. An array or an ArrayList of Confetti is the next step if you are ready for it.
The starter class 
public class Confetti {

    // Instance variable: every Confetti object gets its own size
    private int size;

    // TODO: What else does a piece of confetti need to know about itself?
    // Ideas: x, y, speed, color (r, g, b), rotation, drift

    // Constructor: runs once when a new Confetti object is created
    // No parameters: the piece picks its own random size (3 to 15)
    public Confetti() {
        size = (int)(Math.random()*13+3);
    }

    // Overloaded constructor: the caller chooses the size
    public Confetti(int s) {
        size = s;
    }

    // Getter: lets other classes READ the size
    public int getSize() {
        return size;
    }

    // Setter: lets other classes CHANGE the size
    public void setSize(int s) {
        size = s;
    }

    // TODO: Add a fall() method that moves this piece down the screen

} // end Confetti class

In the sketch, Confetti piece; is declared at the top, piece = new Confetti(); runs once in setup(), and drawConfetti(piece) draws a white square at (400, 80) every frame. A click calls piece.setSize() with a new random size, so the setter is already in use.

Want more? Give each piece a color, a sideways drift, or a spin. Click a piece to remove it. Let pieces pile up at the bottom, or bump into each other. Or pick your own context: instead of confetti, what would you make?

The first forty minutes

What your traffic lights taught us

People shared their own traffic lights and work from their students: pedestrians, crosswalks, a parallax road, a sun on a sine wave, a tractor-trailer, and a crash or two.

  • Name your numbers. One participant replaced every magic number with a named, capitalized constant. A color could not be a constant, because it needs a method call before it exists. A hex value gets around that. Saber’s comment: this was making the case for object orientation without meaning to, because the hard part had become deciding where each block of code should live.
  • Objects were there all along. MakeCode Arcade sprites are objects, and so is anything students have used with a capital letter, such as String. Pointing back to them makes the new unit feel less new. CSAwesome ↗ has physical models that show how objects work.
  • Pedestrians collide. Several students added a walker, and several walkers walked into the car. That is good discussion material, and compound conditions are usually the fix. One teacher asked for a good way into De Morgan’s laws. Joshua’s: moving is not red and not pedestrian button, then rewrite it the other way.
  • Reuse a method, then add to it. In Joshua’s class, a night car calls the day car method and adds a couple of shapes, such as headlights. Students who finish early go much further. He checks in when someone writes dx * dx instead of Math.pow, to find out whether they know what Math.pow does. The project ran more than five class days.
  • Collisions go deep. Jeffrey Thompson’s Collision Detection ↗ starts with two points and builds to polygons, with the math for each case. Some students love it. Games often cheat with rectangles, called hitboxes.
  • Starting and stopping are different states. In the UK, amber shows before green as a get-ready signal, so the car should go straight from stopped to full speed instead of creeping. And a real car keeps going until it reaches the light. Students ask for an eased stop too. The order of states matters, not only which state you are in.
  • The error is often on the line before. A missing bracket or semicolon is reported on the next line. Joshua has students label closing brackets, such as } // end drawLight method, which also builds the vocabulary.
  • AI in the Make stage. One teacher lets students ask an AI tool for help in the Make stage, with specific questions, and reminds them there is no AI on the exam. Another noticed that students who use AI often think they understand the code until they are asked about it.
  • Make sharing a habit. Teachers want students celebrating and questioning each other’s code more, possibly on a set day each week. End-of-unit presentations help students expect to explain their work, and always need more time than planned.
Mini-lecture

Why objects

Once a sketch needs a pile of booleans and variables, every light needs its own state. An object holds that state and the methods that change it. draw() gets shorter: it calls methods, and the objects do the work. This is roughly Unit 3 of AP CS A.

class Light {
  private int x;
  private int y;
  private boolean on;
  // also r, g, b, display(), contains()

  public boolean isOn() {
    return on;
  }

  public void setOn(boolean on) {
    this.on = on;
  }
}
  • Dot notation is not new. Students have used it with strings and with printing. Now they write the methods on the other side of the dot.
  • Private, getter, setter. Private fields can only be touched by the class itself. Other code asks with a getter and changes things with a setter. Students may ask who else would ever touch their variables. It is still good hygiene, and the AP expects it. A good question to ask: can setup() set green.on = true directly? The Session 3 page has the answer.
  • Trace the calls slowly. draw() calls a method, control jumps into the class, the method runs, and control comes back to draw(). With objects, which code runs when gets harder to see, so diagram it. With the traffic light, ask: the car is moving, so where are we in the code, and what runs next? Python Tutor ↗ can step through Java too.
  • Where the code runs matters. Pickcode, the Processing editor, and Eclipse each handle files differently. In Eclipse, the folders have to match the class structure, or Java cannot find the methods.
  • Assess with the sketch you built. Have students diagram each class and its methods, predict what happens in a specific scenario, and take a quiz about the traffic light itself instead of abstract questions.
  • A lighter way to close a unit. Saber showed a student poster: frames from the animation, some code, and a written reflection. Posters go up on the wall and get shown to next year’s class.
With Joshua Hans

From one piece of confetti to a class

Joshua noticed that students who learned Processing first are used to global variables, so instance variables are a much smoother step for them than in past years. He built up to the class in three steps.

  1. One piece, no objects. Variables for location, size, speed, and color. In draw(), the y value changes by the speed, and the piece comes back at the top at a random x once it falls off the bottom, like the car’s wraparound.
  2. Three pieces. A whole set of variables for each piece, and every condition written three times.
  3. Parallel arrays. Joshua taught arrays before objects last year, so students reached for one array per property. Index 0 of every array makes the first piece, index 1 the second, and it scales from 5 to 100 by changing one number. It works, and it is hard to read.

The question that motivates the switch: what if you want to delete just the third piece? With parallel arrays, you have to remove it from every array and keep them lined up. Adding a sideways drift or a spin to one piece gets messy the same way.

The class. The starter Confetti class holds one private field, size, and two constructors that show overloading: one picks a random size, and one takes a size. new Confetti(100) makes a very large square. In the sketch, Confetti is now a type, like int or boolean.

  • Constructors and methods look alike. Students often mix them up. A constructor makes the object, has the name of the class, and has no return type. A method is something an object does, and can be named anything.
  • Watch the capital letters. Saber has students box anything with a capital letter, as a sign they are working with a class. Joshua asks students not to capitalize their own method and variable names, so constructors stand out.
  • Working to a spec. A class is often the first time students write inside someone else’s structure, almost like an API, instead of starting from a blank file.
  • What return does. A question from the group: return makes sense for math functions, but less elsewhere. A getter is a good place to start: getSize() hands back the value of size to whoever asked.

In the breakout rooms, one room moved the drawing code into its own method inside Confetti.java, so each piece draws itself. The other connected confetti to Daniel Shiffman’s flocking sketch: one object first, then many in a data structure, so the main sketch stays short. Many objects also set up collisions and physics, such as confetti piling up at the bottom, which would be close to impossible without them.

Guest

Joshua Davis: a painter whose tools changed

Once you can make a thousand of something, things start to take on a life of their own. That idea runs through Daniel Shiffman’s The Nature of Code ↗ and through much of Joshua Davis’s ↗ work. Being in the Processing world means students are part of a community of artists doing remarkable things, not only doing assignments.

  • Systems he could not control. Joshua moved from Colorado to New York in 1992 to study painting at Pratt. He baked glazed oil paintings in an oven so they would crack differently every time. A Commodore 64 from his dad, computers found on the street, and a campus job building Pratt’s website taught him code. When he realized he could program randomness, he stopped thinking of himself as a painter who used computers. He still calls himself a painter. The weapons changed.
  • An undefined internet. Saber asked when code first felt like art. Joshua said that question comes from today’s internet. In the mid-1990s there was no shopping, no social media, not even CSS. Artists treated the web as a new canvas that anyone in the world could see.
  • Casey, Flash, and Processing. His first job after Pratt paired him with a designer named Casey Reas, who later went to MIT and co-created Processing. Joshua spent about fifteen years in Flash. When it ended, he moved into physical computing, found that the Arduino editor was the Processing editor, and has used Processing ever since.
  • Processing as a shell. Joshua still works in Processing’s Java mode on Linux. His main file only sets things up. Separate classes handle SVG, textures, shaders, colors, and audio. The heavy drawing happens in GLSL shaders on the GPU, so a live show stays at 60 frames a second. Processing orchestrates, and the shaders paint.
  • A tiny draw(). His draw() updates the data and colors, then renders. It matched the point from the mini-lecture: do the work in objects, and keep draw() short.
  • Better programmers write less. Modulo turns eleven lines into one. Objects do the same. Ten people, each wearing a hat, is a mess of arrays at the top of a sketch. A Person with a hat keeps each hat with its owner.
  • One class, fifty times. He showed work built on Shiffman’s flocking example: one particle class, asked for many times, each picking its own direction, color, and behavior within set limits. He sets the canvas, the paints, the strokes, and which colors love or hate each other, says go, and becomes the first person to see what happens.
  • GLSL. Shader code addresses every pixel at once, so there is no real idea of a for loop. That is why it is hard to learn and why it is fast.

His advice for students: when you are starting out, you write more code than you need, so you spend more time on the technical side. The more you learn, the less you write, and the more time you get to be creative.

From the group

Moves to borrow

  • Let the mess come first. Three pieces of confetti with copied variables, or a traffic light full of booleans, makes students want a better way before you show one.
  • Ask about one object. “Delete just the third piece” or “make only this light blink” shows what parallel arrays and global variables make hard.
  • Use student work as the lesson. A pedestrian walking into a car is a better way into compound conditions than a made-up example.
  • Quiz on the sketch you built. Specific scenarios about the traffic light test sequence and state better than abstract questions.
  • Connect to museums. Much of the digital art students see in museums is made with Processing or tools like it. Ask what classes and data structures a piece would need.

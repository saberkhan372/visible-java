Leaving the PDE

The Processing editor did four things for you invisibly: it hid main, it gave you one file for everything, it drew to a window automatically, and it made Run a single keystroke. You are about to lose all four. Here is what to use instead.

Never used Processing? Start with Your first sketch, which installs it and runs one program, then come back here.

Pick an environment

Use whatever your teacher uses. If the choice is yours, these are the sensible options:

Course lesson pages

Nothing to install for reading and tracing. Copy a lesson starter into the school’s Java environment when it is time to compile, test, and save the program.

jGRASP

Free, light, made for learning. Its object viewer draws your variables and objects while the program is paused — the single most useful feature for understanding references.

BlueJ

Objects made visible. Shows classes as boxes and lets you create an object and call its methods by clicking. A gentle first step off the PDE.

IntelliJ IDEA

What professionals use. Free Community edition. More setup and more to ignore, but if you plan to keep programming after this course, learning it now is not wasted.

One rule whatever you pick: the file name must match the public class name exactly. public class Ball lives in Ball.java, capital B and all. In Processing you never had to think about this. Now it is the difference between compiling and not.

Course verification baseline: Java 17. The downloadable workbook projects are compiled and checked with OpenJDK 17 before publication. Use the Java 17 distribution configured by your school; the current authoring verification version is 17.0.20. Processing extensions use a separate optional dependency and never block the standard-Java projects.

Optional, but worth it

If you want to keep the pixels

Nothing about AP CS A requires you to give up graphics. Two ways to keep making things move while writing exam-legal Java:

Processing as a library

Use Processing's core.jar from a normal Java project: write a class that extends PApplet, override draw(), and launch it from main. Everything you already know still works — you just see the class around it now. Doing this once explains the whole first month of the course.

Code.org Java Lab

Free, in the browser, nothing to install. Its Neighborhood and Theater environments let you write real classes with a real main and still get animation, images and sound on screen. The closest thing to the Processing feedback loop that stays inside AP Java.

Week one

The errors you are about to meet

Compiler errors look hostile and are mostly not. Each of these has one usual cause.

non-static method move() cannot be referenced from a static context
The one you'll see most. You are inside main, which is static, and you tried to call a method that belongs to an object. Make an object first: Ball b = new Ball(); b.move();
incompatible types: possible lossy conversion from double to float
You wrote float x = 3.5;. Use double. Java will not silently shrink a number for you the way Processing did.
incompatible types: possible lossy conversion from double to int
Same idea one type down — usually assigning the result of division or Math.random() to an int. Cast it: (int)(...).
cannot find symbol
Java does not know that name. A typo, wrong capitalisation, a variable declared inside a block you have now left, or a Processing function that does not exist here (ellipse, random, map).
class Ball is public, should be declared in a file named Ball.java
Rename the file, or rename the class. They must match exactly.
missing return statement
A method that promises a return type has a path through it that returns nothing — usually an if with no else.
variable count might not have been initialized
You declared it but never gave it a value before reading it. Local variables do not default to zero; only instance variables do.
constructor Ball in class Ball cannot be applied to given types
You called new Ball(...) with the wrong number or type of arguments. Check the constructor's parameter list.

And at runtime

  • NullPointerException — you called a method on something that is null. Very often an array of objects you created but never filled. See trap 15.
  • ArrayIndexOutOfBoundsException — an index below 0 or at least length. Almost always <= where you wanted <. See trap 14.
  • StringIndexOutOfBoundsException — same thing on a string, usually from substring with an end index past the last character.
  • ArithmeticException: / by zero — integer division by zero. Note that double division by zero does not throw; it gives Infinity.

Read stack traces from the top. The first line names the exception and the message; the next line with your file name in it is where to look. Everything below that is Java's own machinery and you can ignore it.

Two things to bookmark now

  • The Java Quick Reference — the exact list of library methods you are allowed to use, and the exact list you will have in front of you on exam day. It is two pages. Read it now so nothing on it is a surprise in May, and so you stop reaching for methods that are not on it.
  • Java Tutor — paste code in, step forwards and backwards, watch the objects and arrows. Use it every single time you are confused about what a reference is pointing at.

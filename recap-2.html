Before November 22

Finish the traffic light

Open visible java traffic in Pickcode. Try what you have time for, and bring it to the start of Session 3. Fuller directions will follow in Google Classroom later this week.

  1. Predict. Read the code before running it. What will you see? What happens when you click each light?
  2. Run. Click all three lights. Were you right?
  3. Investigate. Find the code that checks a click on the red light. Why can’t you get back to green?
  4. Modify. Make yellow and green clickable.
  5. Make. Drive on green, slow on yellow, stop on red. As a bonus, wrap the car around the screen.
  6. Put the light on a timer. Make it change by itself every few seconds. Two ways to do this are described below.
Stuck on the clicks? Show one way

The starter measures the distance from the mouse to the red light’s center at (510, 55) and nothing else, so red is the only light a click can reach. The other two lights are drawn at (510, 115) and (510, 175). Each needs its own check, with its own variable name.

public void mousePressed() {
  double redDistance = calculateDistance(mouseX, mouseY, 510, 55);
  double yellowDistance = calculateDistance(mouseX, mouseY, 510, 115);
  double greenDistance = calculateDistance(mouseX, mouseY, 510, 175);

  if (redDistance <= 25) {
    state = "red";
  } else if (yellowDistance <= 25) {
    state = "yellow";
  } else if (greenDistance <= 25) {
    state = "green";
  }
}

Each light is 50 across, so a click within 25 of its center is inside it. A click anywhere else leaves state as it was.

Want more? Ideas from the group: a pedestrian button that makes the car stop no matter what, a sky that moves from day to night, and a sun that follows a sine wave.

The first forty minutes

What your stamp scenes taught us

People shared a snowman, leaves that turn and change color, a scarecrow, a mushroom, and the whole scene rebuilt as a regular Java project.

  • Draw around (0, 0). A snowman stamped down and to the right of the pointer. Its circles were drawn around (200, 100), and translate(x, y) had already moved (0, 0) to the mouse. Someone in the group spotted it from the picture. Saber’s advice: when an error is this easy to see, celebrate it and put it in front of the class.
  • Choose a reference point. Joshua has students pick one anchor point on paper and place every other shape relative to it, such as x + 60 or y - 105. Once shapes move, anything not tied to that point gets left behind. He finds that slowing down to plan makes students faster later.
  • Math.random() is a stretch and a shift. It gives a number from 0 up to, but not including, 1. Multiplying stretches the range, adding shifts it, and a cast to int drops the decimals. Processing’s random(low, high) is easier, and Math.random() is the one on the exam. CSAwesome ↗ has a lesson that builds the formula step by step.
  • An arc is a sliced ellipse. The first four arguments match ellipse, followed by a start and a stop angle. Zero points east, and the angles increase clockwise: 90 is south, 180 is west, 270 is north. radians(180) lets students think in degrees.
  • Scale and layering. A scale argument lets one method draw the same shape at any size, which can suggest depth. Whatever is stamped later lands on top. Joshua’s students are using a scalable star to put 50 stars on a flag with loops. scale ↗
  • Processing is a Java library. One participant moved the scene into a regular Java project with GitHub and VS Code: a main method loads the library and starts a separate sketch class, the same two files Pickcode shows. GitHub Codespaces is one way to run that on Chromebooks.
  • int, float, and double. Several people hit type errors while adding randomness. Processing’s drawing methods take float, which AP CS A does not cover. Java widens an int to a float by itself. Going from a double to a float could lose data, so Java asks for an explicit cast. The same “lossy conversion” error appears in AP work when a double goes into an int.
Mini-lecture

The draw loop and one if

draw() works like main, except that it runs again every frame. Last week it was empty. Put a moving shape and an if inside it, and the sketch checks its own state about 60 times a second.

float carX = 0;
float busX = 0;

void draw() {
  background(230);
  rect(carX, 120, 60, 30);
  carX = carX + 3;
  rect(busX, 240, 100, 40);
  busX = busX + 1;

  if (carX > width) {
    carX = 0;
  }
}

The car has a wraparound: once carX passes the right edge, it goes back to 0. Nothing asks about busX, so the bus leaves and does not come back. Saber teaches wraparound first in his animation unit, then sets small challenges, such as making it travel the other way.

void keyPressed() {
  if (key == ' ') {
    lightIsGreen = !lightIsGreen;
  }
}

A boolean can hold the state of a light, and ! flips it. The car reads that one variable to decide whether to move. Students often write if (lightIsGreen == true). Writing if (lightIsGreen) shows they understand that the variable already holds the answer. Both sketches run in the slides.

  • PRIMM. Predict, run, investigate, modify, make. Students read working code and say what it will do before they change anything, which is less daunting than a blank editor.
  • Where this sits. This is Unit 2 of AP CS A, about a third of the way through the year. Loops belong to the same unit.
  • A project to borrow. Saber’s students make an animation that must include a wraparound, a bounce, and a color change. It runs over several days: a drawing, pseudocode, coding, a draft share. Then each student makes a poster with the first, middle, and last frames, some of the code, and a short summary, and the posters go up on the wall. The class works from Daniel Shiffman’s Learning Processing ↗.
With Joshua Hans

From a student’s scene to a traffic light

Joshua started from a shared mushroom stamp and asked the question he would ask a student: how could you make sure mushrooms only grow on the grass?

if (key == 'h') {
  if (mouseX >= 300) {
    drawMushroom(mouseX, mouseY, 1);
  }
}

Mushrooms appeared on the right half of the canvas, sky included, and nowhere on the left. The condition asks about mouseX and the grass is a question about mouseY. The group caught it in the chat. Mixing up x and y is a very common slip, and the picture gives it away. A nested if like this one is also a way into &&.

The traffic light starter then ran as a PRIMM activity, with about fifteen minutes in two breakout rooms.

  • The state is a String, on purpose. state.equals("red") compares the characters. == asks whether two variables refer to the same object, which sometimes works and cannot be trusted. Strings are objects, and that is why they have methods such as substring.
  • Print the distances. One room printed all three distances on every click. Watching which number dropped below 25 explained the condition better than reading it, and clicking right at the edge of a light gave values like 26.
  • Short or readable? The distance call can go straight inside the if, which skips two calculations, or into named variables, which is easier to read. else if stops checking after the first match. The group also talked about adding comments or Javadoc, and whether a click outside every light should switch them all off.
  • Say the algorithm first. The other room talked the light changes through before writing any code. Saber asks students to explain a process as if to someone who has never programmed.
Two ways to count

Putting the light on a timer

Processing counts frames in frameCount, at about 60 a second. A sketch can read it and cannot set it back to zero.

// Your own counter: easier to explain
counter = counter + 1;
if (counter >= 180) {
  // change the light here
  counter = 0;
}

// Modulo: shorter
if (frameCount % 180 == 0) {
  // change the light here
}

Both change the light every 180 frames, about three seconds. Saber starts with the counter, because many students do not yet see why a remainder would help. Students who write out a long run of if statements for 180, 360, 540 feel the problem that % solves. Joshua printed frameCount next to frameCount % 180, and the console showed the second number climbing to 179 and returning to 0.

Stopping the car where it is. A first attempt set carX = 0 on red, which sent the car back to the left edge. Changing carX only when the light is green stops it in place. A speed variable does the same job and also allows a slow yellow: always add carSpeed to carX, and let the light set carSpeed to 3, 1, or 0.

From the group

Moves to borrow

  • Share work at the start. A few minutes of looking at pictures gives everyone a way into the code. Ask what they see on the canvas, then what that says about the code.
  • Plan on graph paper. Sketch the shape and mark its reference point before typing. One teacher keeps graph paper on hand, though students reach for it only once they are really stuck.
  • Use Desmos alongside the code. Joshua’s students use sliders to explore period and amplitude before moving a sun along a sine wave. Sine and cosine together give an x and a y, which reinforces that every point needs two numbers.
  • Build it artificially first. For a day and night cycle, get a sky that changes by itself working, then replace the made-up clock with real local time.
  • Let projects open the next unit. A question about a student’s own scene, such as where mushrooms may grow, introduces conditionals before the unit starts.
